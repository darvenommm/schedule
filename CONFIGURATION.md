# Настройка нарядов и трёх графиков уборок

Все четыре расписания рассчитываются совместно: наряды, уборки кубаря каждого из двух взводов и общий график санузлов. На каждый день назначаются три человека в наряд и шесть других людей на уборки.

Основной файл — [`config/schedule.yaml`](config/schedule.yaml), список людей — [`config/people.yaml`](config/people.yaml). Настройки проверяются Pydantic: неизвестные поля и неправильные типы отклоняются.

Для запуска нужны Python 3.14 или новее, uv и отдельно установленный MiniZinc с нужным решателем. Проверка MiniZinc и установка зависимостей Python:

```bash
minizinc --version
minizinc --solvers
uv sync
```

Команда `minizinc` должна быть доступна в `PATH`. Python-пакет `minizinc` предоставляет интеграцию, но не устанавливает компилятор и решатели. Если установлен AppImage и терминал не видит команду, настройте его интеграцию по [официальной инструкции MiniZinc](https://docs.minizinc.org/en/latest/installation.html#appimage).

Запуск из корня проекта:

```bash
uv run schedure --config config/schedule.yaml
```

Эквивалентный запуск: `uv run python -m src --config config/schedule.yaml`. Если `--config` опущен, программа ищет `config/schedule.yaml` относительно текущего каталога.

Индикатор показывает завершённые этапы программы и время текущей операции. Во время поиска работает анимация активности; во время экспорта видны подготовленные листы. Это не процент достижения оптимума и не оценка оставшегося времени поиска. При выводе в файл анимация заменяется строками этапов, чтобы не засорять журнал управляющими символами.

Для запуска без индикаторов и строк этапов:

```bash
uv run schedure --config config/schedule.yaml --no-progress
```

Ключ `--no-progress` задаётся в командной строке, а не в YAML. Ошибки и итоговый путь к Excel выводятся независимо от него. `Ctrl+C` прерывает расчёт и останавливает индикатор.

Перед запуском обновите месяц и год, данные людей, историю отхоженных нарядов и список предыдущего наряда. Затем выберите режим поиска и проверьте имя выходного файла.

## Полный пример конфигурации

```yaml
year: 2026
month: 12

people_file: people.yaml
output_file: ../output/duties-{year:04d}-{month:02d}.xlsx

solver:
    name: cp-sat
    time_limit_seconds: 300
    free_search: false
    random_seed: null
    processes: 4
    optimisation_level: 1
    require_optimal: false

preferences:
    preferred_gap_days: 5
    spacing_weight: 1
    balance_weight: 10
    duty_role_weight: 20
    cleaning_preferred_gap_days: 3
    cleaning_spacing_weight: 1
    cleaning_balance_weight: 10

cleaning:
    enabled: true

# Заполните фактическими ФИО всех троих за последний день предыдущего месяца.
# При [] граница месяца не проверяется.
previous_month_last_day: []
```

Это пример ограниченного по времени поиска для установленного CP-SAT и процессора, на котором можно выделить четыре потока поиска. Он разрешает выгрузку допустимого решения без доказательства оптимальности. Сравните его с Chuffed на своих данных, прежде чем выбирать постоянный вариант.

Для поиска без ограничения времени с экспортом только доказанно оптимального решения замените `time_limit_seconds` на `null` и `require_optimal` на `true`. Остальные параметры можно оставить как в примере.

## Месяц, файлы и граница месяца

| Поле | Допустимые значения | Назначение |
| --- | --- | --- |
| `year` | Целое число 1–9999 | Год расписания. |
| `month` | Целое число 1–12 | Месяц; число дней определяется автоматически. |
| `people_file` | Непустая строка; по умолчанию `people.yaml` | Путь к списку людей. |
| `output_file` | Непустая строка с расширением `.xlsx` | Путь к результату, поддерживает подстановки года и месяца. |
| `previous_month_last_day` | Список полных ФИО; по умолчанию `[]` | Кто заступал в последний день предыдущего месяца: этих людей нельзя назначать на первое число. |

Пути считаются относительно YAML-файла, а не текущего каталога терминала. В `output_file` поддерживаются `{year}` и `{month}`, а также числовые форматы `d`, `02d` и `04d`. Используйте `../output/duties-{year:04d}-{month:02d}.xlsx`: для декабря 2026 года получится `duties-2026-12.xlsx`, для января 2027 года — `duties-2027-01.xlsx`. Достаточно изменить `year` и `month`. Фиксированное имя без подстановок тоже допустимо. Неизвестные подстановки отклоняются до расчёта.

При повторном запуске того же месяца тот же выходной файл перезаписывается после успешного расчёта.

Перед расчётом укажите в `previous_month_last_day` всех троих из последнего наряда предыдущего месяца: дежурного и обоих дневальных. Для декабря это наряд за 30 ноября; для января — за 31 декабря предыдущего года. Это люди из наряда непосредственно перед первым днём нового расписания.

Например, если в тот день заступали следующие люди, раздел будет выглядеть так (замените пример фактическими ФИО):

```yaml
previous_month_last_day:
    - Латута Дмитрий Юрьевич
    - Бугаков Данила Андреевич
    - Вишневский Михаил Михайлович
```

ФИО должны точно совпадать с `full_name` из списка людей: «Фамилия Имя Отчество». Эти люди не получают ни наряд, ни уборку на первое число. При пустом списке история назначений на границе месяца неизвестна, и ограничения на этой границе не проверяются. Одного счётчика `completed_duties` недостаточно, чтобы проверить интервалы между конкретными датами разных месяцев.

## Обязательные правила

Эти правила встроены в модель и не отключаются весами предпочтений:

- Ежедневно назначаются три разных человека: один дежурный и два дневальных.
- Дежурным может быть только человек с `can_be_on_duty: true`.
- Дневальным может быть любой человек, в том числе допущенный к дежурству.
- Запрещены назначения в два последовательных дня, независимо от роли.
- Для людей с `usually_goes_to_sirius: true` запрещены любые назначения по средам.
- Назначения на границе месяца учитываются через `previous_month_last_day`.
- Ежедневно кубарь каждого взвода убирают два человека из этого взвода, санузлы — два человека из любого взвода.
- Все шесть уборщиков одного дня различны: человек не убирает одновременно кубарь и санузлы.
- Нельзя убирать в день наряда или на следующий день после наряда, независимо от роли в наряде.

### Поездки в Сириус и уборки по четвергам

В среду наряд для ездящих в Сириус запрещён обязательно. Уборку в четверг для них допускаем только как нежелательный вариант: решатель сначала минимизирует общее количество таких назначений и уже затем улучшает остальные предпочтения.

Этот приоритет реализован автоматически рассчитанным коэффициентом: одно дополнительное назначение перед Сириусом стоит больше всех остальных возможных штрафов вместе. Изменение весов обычных предпочтений не отменяет этого приоритета. При ограничении времени найденное количество ещё может быть неоптимальным; гарантия минимума появляется при доказанной оптимальности.

На исходном списке из 14 человек 6 ездят в Сириус. В среду трое из остальных 8 заступают в наряд и в четверг не могут убирать. Не ездящих доступно максимум 5, а уборщиков нужно 6: как минимум одна уборка в такой четверг должна достаться ездящему в Сириус. Для первого числа, если это четверг, результат зависит от заполненной истории предыдущего наряда.

В разделе `cleaning` доступно поле `enabled` (булево, по умолчанию `true`). При `false` рассчитываются только наряды и выгружаются прежние два листа Excel. Состав взводов и данные людей при этом остаются обязательными.

Если правила несовместимы, увеличение времени или изменение весов не создаст допустимое решение.

## Предпочтения и качество расписания

| Поле в `preferences` | Значение по умолчанию | Допустимые значения | Что регулирует |
| --- | --- | --- | --- |
| `preferred_gap_days` | `5` | Целое число 2–31 | Целевое расстояние в днях между датами нарядов. |
| `spacing_weight` | `1` | Целое число 0–1000 | Важность увеличения интервалов между нарядами. |
| `balance_weight` | `10` | Целое число 0–1000 | Важность равномерной общей нагрузки с учётом истории. |
| `duty_role_weight` | `20` | Целое число 0–1000 | Предпочтение назначать допущенных людей дежурными вместо дневальных. |
| `cleaning_preferred_gap_days` | `3` | Целое число 2–31 | Целевое расстояние между любыми двумя уборками человека. |
| `cleaning_spacing_weight` | `1` | Целое число 0–1000 | Важность интервалов между уборками. |
| `cleaning_balance_weight` | `10` | Целое число 0–1000 | Важность равномерного количества уборок отдельно в каждом графике. |

Решатель минимизирует сумму:

```text
штраф = коэффициент_приоритета × уборки_в_четверг_перед_Сириусом
      + spacing_weight × штраф_интервалов
      + balance_weight × штраф_баланса
      + duty_role_weight × штраф_роли
      + cleaning_spacing_weight × штраф_интервалов_уборок
      + cleaning_balance_weight × штраф_баланса_уборок
```

Штраф интервалов считается для всех пар нарядов одного человека в расчётном месяце. Если расстояние меньше `preferred_gap_days`, добавляется квадрат недостающего расстояния. Например, при цели 5 дней расстояние 3 дня даёт штраф 4, расстояние 4 дня — штраф 1, а расстояние 5 дней и больше — 0. Расстояние измеряется между датами: между 1 и 6 числом — 5 дней. Это предпочтение; обязательный запрет последовательных дней действует отдельно.

Штраф баланса — сумма абсолютных разностей общей нагрузки для всех пар людей. Общая нагрузка человека равна `completed_duties` плюс все его назначения за расчётный месяц. Дежурство и назначение дневальным считаются одним нарядом каждое.

Штраф роли — количество назначений допущенных к дежурству людей дневальными. Общее число дежурств фиксировано: один дежурный на каждый день. Поэтому критерий уменьшает число дополнительных назначений таких людей дневальными, а не увеличивает общее количество дежурных мест. Отдельного критерия выравнивания числа именно дежурств между допущенными людьми пока нет.

Интервалы уборок оцениваются по той же квадратичной схеме, но с параметром `cleaning_preferred_gap_days`. Учитываются пары любых уборок: кубарь–кубарь, санузлы–санузлы и кубарь–санузлы. Уборки в последовательные дни разрешены, но штрафуются при ненулевом `cleaning_spacing_weight`.

Баланс уборок считается отдельно для каждого графика. По кубарю сравниваются количества у людей своего взвода; по санузлам — у всех людей. История уборок пока не ведётся: баланс и интервалы оцениваются внутри расчётного месяца. Абсолютное равенство не обязательно достижимо из-за числа дней и остальных ограничений.

Практические настройки:

- Чтобы увеличить интервалы, повышайте `spacing_weight` относительно остальных весов.
- Чтобы выровнять нагрузку, повышайте `balance_weight`.
- Чтобы допущенные люди преимущественно были дежурными, повышайте `duty_role_weight`.
- Чтобы разнести уборки по датам, повышайте `cleaning_spacing_weight`; чтобы выровнять их количество в каждом графике — `cleaning_balance_weight`.
- Значение `0` отключает соответствующий критерий. Оно не отключает обязательные правила.
- Меняйте один параметр за раз. Веса допускают компромиссы: даже большой вес не превращает предпочтение в обязательное правило.

Сравнивайте итоговые штрафы только при одинаковых людях, истории, месяце, правилах и весах. После изменения весов само численное значение штрафа уже несопоставимо с предыдущим запуском. Если все пять весов равны нулю, оптимизируется только число уборок в четверг перед Сириусом; если уборки отключены, любое допустимое расписание нарядов при нулевых весах оптимально.

## Общие опции решателя

Все поля расположены в разделе `solver`.

| Поле | По умолчанию в Python | Допустимые значения | Назначение |
| --- | --- | --- | --- |
| `name` | `chuffed` | Непустая строка | Имя или идентификатор установленного решателя. |
| `time_limit_seconds` | `30` | Целое число от 1 или `null` | Лимит расчёта, передаваемый MiniZinc. `null` убирает ограничение времени. |
| `free_search` | `false` | `true` / `false` | Разрешает решателю выбирать собственную стратегию поиска. |
| `random_seed` | `null` | Целое число 0–2147483647 или `null` | Начальное значение генератора случайных чисел. |
| `processes` | `null` | Целое число от 1 или `null` | Число потоков/работников поиска в поддерживающем решателе. |
| `optimisation_level` | `1` | Целое число 0–5 | Оптимизация компиляции модели MiniZinc. |
| `require_optimal` | `false` | `true` / `false` | Разрешён ли экспорт только после доказательства оптимальности. |

Значения в самом YAML перекрывают значения по умолчанию. Например, при отсутствии `time_limit_seconds` Python использует 30 секунд, а `null` явно отключает лимит. В полном примере выше показан ограниченный режим на 300 секунд.

`free_search: true` не гарантирует ускорения. `random_seed` может изменить ход поиска, но результат зависит от того, использует ли стратегия случайный выбор. Один и тот же seed не гарантирует идентичный результат между версиями решателя и при параллельном поиске.

`optimisation_level` — не настройка «насколько хорошее расписание искать». Начните с `1`. Значение `0` отключает оптимизацию компиляции; более высокие уровни могут увеличить подготовку задачи, а некоторые используют дополнительную обработку с Gecode. Увеличение уровня не гарантирует улучшения результата за тот же лимит.

## Различия между решателями

Поддержка в таблице сверена с конфигурациями решателей установленного комплекта MiniZinc 2.10.1. Для другой установки проверьте доступные имена и параметры:

```bash
minizinc --solvers
minizinc --help chuffed
minizinc --help cp-sat
minizinc --help gecode
```

| Возможность | Chuffed (`chuffed`) | OR-Tools CP-SAT (`cp-sat`) | Gecode (`gecode`) |
| --- | --- | --- | --- |
| Ограничение времени | Да | Да | Да |
| `free_search` | Да | Да | Да |
| `random_seed` | Да | Да | Да |
| `processes` | Оставить `null`: параллельный поиск не поддерживается | Поддерживается | Поддерживается |
| Доказательство оптимальности | Возможно при завершении полного поиска | Возможно при завершении полного поиска | Возможно при завершении полного поиска |
| Использование видеокарты для этого поиска | Нет | Нет | Нет |

Программа проверяет поддержку `free_search`, `random_seed` и `processes` по метаданным выбранного решателя. Например, для Chuffed значение `processes: 4` вызовет ошибку; используйте `null`.

### Chuffed: отправная точка

Замените раздел `solver` на:

```yaml
solver:
    name: chuffed
    time_limit_seconds: 300
    free_search: false
    random_seed: null
    processes: null
    optimisation_level: 1
    require_optimal: false
```

Сначала получите допустимое решение, затем сравните отдельные запуски с `free_search: true` и разными значениями `random_seed`. На текущей модели в короткой проверке сочетание `free_search: false` и `random_seed: null` дало первое решение быстрее, чем `true` и `42`. Это наблюдение для конкретного запуска, а не общее правило.

### OR-Tools CP-SAT: поиск на нескольких ядрах CPU

```yaml
solver:
    name: cp-sat
    time_limit_seconds: 300
    free_search: false
    random_seed: null
    processes: 4
    optimisation_level: 1
    require_optimal: false
```

Сравните `processes: 1`, `4` и `8`, если процессор и доступная память позволяют. Большее число работников меняет стратегию поиска и не гарантирует ускорения. Не выделяйте все ресурсы, если компьютер нужен для другой работы. Мощная видеокарта этот поиск не ускоряет.

### Gecode: альтернативный решатель для сравнения

```yaml
solver:
    name: gecode
    time_limit_seconds: 300
    free_search: false
    random_seed: null
    processes: 1
    optimisation_level: 1
    require_optimal: false
```

Начните с одного работника, затем сравните с несколькими. Оцените время до первого решения и итоговый штраф при одинаковом лимите. Результат сравнения с Chuffed и CP-SAT зависит от модели и исходных данных.

### Другие решатели и специальные флаги

Другой установленный решатель можно выбрать через `name`, если он совместим с моделью. Однако YAML приложения поддерживает только поля из таблицы выше. Специальные флаги из `minizinc --help`, например настройки перезапусков Chuffed или поле `--params` CP-SAT, сейчас не передаются через YAML. Их добавление требует расширения Python-интеграции. Произвольный ключ в конфигурации будет отклонён.

## Как добиться доказанной оптимальности

Замените раздел `solver` следующим:

```yaml
solver:
    name: cp-sat
    time_limit_seconds: null
    free_search: false
    random_seed: null
    processes: 4
    optimisation_level: 1
    require_optimal: true
```

`time_limit_seconds: null` позволяет продолжать поиск без лимита. `require_optimal: true` проверяет итоговый статус и запрещает экспорт, пока оптимальность не доказана; сам флаг не ускоряет поиск и не включает другой алгоритм. Поиск может занять длительное время.

Можно оставить конечный лимит и включить `require_optimal: true`: если доказательство не получено к его окончанию, программа сообщит об этом и не выгрузит новый Excel. Уже существующий файл от предыдущего запуска при такой ошибке остаётся на месте.

Доказательство означает, что лучшего расписания по заданной сумме штрафов при текущих обязательных правилах нет. Оно не означает единственность расписания и не оценивает правила, которые не включены в модель.

## Как читать результат

| Сообщение | Значение | Следующий шаг |
| --- | --- | --- |
| «Оптимальность доказана» | Решение оптимально по текущей целевой функции. | Оценить, соответствуют ли выбранные веса вашим предпочтениям. |
| «Найдено допустимое расписание; оптимальность не доказана» | Все обязательные правила выполнены, но может существовать лучший вариант. | Увеличить время или сравнить решатели и стратегии. |
| «Решение не найдено» | Решатель не нашёл допустимый вариант за отведённое время либо завершился без решения. | Увеличить лимит, сменить стратегию или решатель. Это не доказательство невозможности. |
| «Расписание невозможно» | Решатель доказал несовместимость обязательных ограничений. | Проверить людей, допуски, среду и границу месяца. |

Запуски независимы: новый запуск не продолжает предыдущий и не получает автоматически его лучшее решение. Для сравнения сохраняйте результаты под разными `output_file`.

## Что будет в Excel

После успешного расчёта терминал выводит фактический путь к `.xlsx`, итоговый штраф и статус оптимальности. Имя файла формируется из шаблона `output_file` и выбранных `year` и `month`.

- **По людям** — строки с ФИО, столбцы по дням месяца, отметки `Деж` и `Дн`, число дежурств, число назначений дневальным, всего нарядов за месяц, история до месяца и итог с историей.
- **По дням** — дата, день недели, дежурный, два дневальных и все шесть уборщиков.
- **Кубарь 1 взвод**, **Кубарь 2 взвод** — по отдельному листу на взвод, даты уборок каждого человека и итоговое количество.
- **Санузлы** — общий график на всех людей с датами уборок и итогами.
- **Итоги** — количество нарядов, уборок по каждому графику и суммарное число назначений за месяц. Также указаны общий штраф и статус оптимальности.

`Деж` означает дежурного, `Дн` — дневального, `У` — уборку. Дежурство и назначение дневальным увеличивают число нарядов; уборки считаются отдельно. Все уборки имеют одинаковое оформление: отдельных цветов, столбцов и подписей для уборок перед Сириусом нет. Их минимизация по-прежнему имеет высший приоритет при расчёте. Расчёт включает выходные и праздники как обычные календарные дни; отдельных ограничений для праздников в модели нет.

Если расчёт закончился ошибкой, новый файл не выгружается, но старый файл по тому же пути может остаться от предыдущего запуска. Проверяйте сообщение терминала и месяц в заголовке таблицы.

Запись Excel выполняется через временный файл в каталоге результата. Прежний файл заменяется после успешного сохранения, чтобы ошибка записи не повредила предыдущий результат.

## Настройка списка людей

Каждая запись в `people.yaml` содержит:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `last_name` | Непустая строка | Фамилия. |
| `first_name` | Непустая строка | Имя. |
| `patronymic` | Непустая строка | Отчество. |
| `can_be_on_duty` | `true` / `false` | Допуск к роли дежурного. |
| `completed_duties` | Целое неотрицательное число | Количество уже отхоженных нарядов до расчётного месяца. |
| `usually_goes_to_sirius` | `true` / `false` | Запрет назначения на среду. |
| `platoon` | Целое число `1` или `2` | Взвод; ограничивает выбор уборщиков кубаря. |

Для `usually_goes_to_sirius` запрет среды относится к нарядам. Уборка по четвергам для таких людей разрешена как нежелательное назначение с высшим приоритетом минимизации.

Указывайте историю на начало месяца. Создание плана автоматически не увеличивает `completed_duties`: запланированный наряд ещё не считается отхоженным.

## Частые ошибки YAML

- Используйте пробелы для отступов, а не табуляцию.
- Числа записывайте без кавычек: `300`, а не `"300"`.
- Булевы значения записывайте как `true` и `false`, без кавычек.
- Отсутствие лимита задавайте как `null`, а не `0` и не строку `"null"`.
- Параметры поиска размещайте внутри `solver`, веса — внутри `preferences`.
- Не дублируйте ключи: вносите изменения в существующий раздел, а не добавляйте второй `solver` в конец файла.
- В шаблоне `output_file` допустимы только `year` и `month`; например, `{day}` или `{month:invalid}` отклоняются до поиска.
- Не подменяйте фактический предыдущий наряд примером из документации: это изменит запрет назначений на первое число.

## Проверка проекта

```bash
uv run python -m unittest discover -s tests -v
```

Проверки включают правила назначения, валидацию настроек, подстановку года и месяца в имя файла, Excel, сохранность прежнего файла при ошибке записи, индикаторы прогресса и интеграцию с решателем. Проверки реального расчёта пропускаются, если команда `minizinc` отсутствует; проверка Excel требует установленного `openpyxl`. Обнаруженная команда MiniZinc также должна реально запускаться, а нужный решатель — быть установлен.
