# Автоматическое составление расписаний

Программа совместно составляет четыре расписания на выбранный месяц и выгружает их в Excel: наряды, уборки кубаря 1-го взвода, уборки кубаря 2-го взвода и уборки санузлов.

## Технологии

- **Python** — основной язык приложения: загрузка и проверка данных, подготовка задачи, запуск расчёта и обработка результата.
- **YAML** — формат конфигурационного файла для выбора месяца, задания весов предпочтений, выбора решателя и настройки поиска. Обязательные правила нарядов встроены в модель.
- **MiniZinc** — описание переменных, обязательных ограничений и целевой функции для учёта предпочтений.
- **Python-пакет `minizinc`** — интеграция приложения с MiniZinc: передача параметров модели, выбор решателя, запуск расчёта и получение результата. Для работы необходимы установленный MiniZinc и доступный ему решатель.
- **Pydantic** — проверка конфигурации и данных людей; **openpyxl** — создание Excel.

## Принципы реализации

Все четыре расписания рассчитываются в одной модели с общими ограничениями для людей и дней. Это позволяет учитывать наряды при назначении уборок и запрещать одновременную уборку нескольких помещений одним человеком.

Обязательные правила задаются ограничениями MiniZinc. Желательные правила учитываются через штрафы в целевой функции; их веса настраиваются в YAML.

Параметры и исходные данные отделяются от логики модели. Через YAML изменяются данные и веса предпочтений. Изменение обязательных правил или добавление нового типа правила может потребовать изменения модели MiniZinc и кода Python.

Код Python организуется с использованием ООП: объекты предметной области и компонент управления расчётом отделяются от загрузки конфигурации и интеграции с MiniZinc.

## Пользователи

Список пользователей хранится в `config/people.yaml`. Каждая запись содержит фамилию (`last_name`), имя (`first_name`) и отчество (`patronymic`). Класс `Person` и функция загрузки определены в `src/people.py`. Pydantic проверяет обязательные поля, типы, непустые значения и отсутствие неизвестных полей.

Поле `can_be_on_duty` указывает, может ли пользователь быть дежурным. Поле `completed_duties` хранит количество отхоженных нарядов на начало расчётного месяца и должно быть целым неотрицательным числом. Перед новым месяцем актуализируйте историю по фактически отхоженным нарядам.

Поле `usually_goes_to_sirius` указывает, ездит ли пользователь обычно в Сириус.

Обязательное поле `platoon` задаёт взвод: `1` или `2`. Кубарь человек убирает только в своём взводе, санузлы — независимо от взвода.

Пример загрузки из корня проекта:

```python
from src.people import load_people

people = load_people("config/people.yaml")
for person in people:
    print(person.full_name)
```

## Расписание нарядов

Подробная [инструкция по настройке YAML и выбору решателя](CONFIGURATION.md) содержит описание всех опций и готовые примеры для Chuffed, CP-SAT и Gecode.

Настройки находятся в `config/schedule.yaml`: год и месяц, файл пользователей, путь к Excel, решатель, время расчёта и веса предпочтений. Пути внутри YAML считаются относительно самого конфигурационного файла. Шаблон `output_file: ../output/duties-{year:04d}-{month:02d}.xlsx` автоматически подставляет выбранные год и месяц; например, для декабря 2026 года получится `duties-2026-12.xlsx`.

Для запуска нужны Python 3.14 или новее, uv, MiniZinc и установленный решатель. Из корня проекта установите зависимости Python:

```bash
uv sync
```

Перед каждым расчётом:

1. Установите `year` и `month` в `config/schedule.yaml`.
2. Проверьте список людей, допуски, поездки в Сириус и историю `completed_duties` в `config/people.yaml`.
3. Укажите в `previous_month_last_day` ФИО дежурного и обоих дневальных из наряда за последний день предыдущего месяца. Не копируйте пример из инструкции вместо фактических данных.
4. Выберите решатель и режим поиска: ограниченный по времени или до доказательства оптимальности.

Запустите расчёт:

```bash
uv run schedure --config config/schedule.yaml
```

Также доступен запуск `uv run python -m src --config config/schedule.yaml`. Аргумент `--config` можно опустить: по умолчанию читается `config/schedule.yaml` относительно текущего каталога.

Во время работы терминал показывает индикатор семи этапов: загрузка конфигурации, загрузка пользователей, проверка данных, подготовка модели, поиск, проверка результата и экспорт. Для поиска отображается прошедшее время, а для экспорта — число подготовленных листов. Полоса отражает завершённые этапы программы, а не процент достижения оптимума: решатель не сообщает достоверное оставшееся время поиска. При перенаправлении вывода вместо анимации печатаются обычные строки этапов.

Отключить индикаторы и сообщения об этапах:

```bash
uv run schedure --config config/schedule.yaml --no-progress
```

Отдельно необходимы [MiniZinc и решатель](https://www.minizinc.org/downloads/). Исполняемый файл `minizinc` должен быть доступен в `PATH`. Проверьте установку командами `minizinc --version` и `minizinc --solvers`. Сам Python-пакет `minizinc` не устанавливает компилятор и решатели.

Режим поиска выбирается в `solver`. Для пробного расчёта используйте `time_limit_seconds: 300` и `require_optimal: false`. Для поиска до доказательства оптимальности — `time_limit_seconds: null` и `require_optimal: true`; такой запуск может работать долго. Если раздел `solver` отсутствует, Python использует Chuffed с лимитом 30 секунд.

Обязательные правила:

- На каждый календарный день месяца назначаются три разных человека: один дежурный и два дневальных.
- Дежурным назначается только человек с `can_be_on_duty: true`. Дневальным может быть любой, включая допущенных к дежурству.
- Один человек не назначается в два последовательных календарных дня независимо от роли.
- Человек с `usually_goes_to_sirius: true` не назначается по средам ни на одну из ролей.
- Перед расчётом заполните `previous_month_last_day` полными ФИО всех троих из наряда в последний день предыдущего месяца: дежурного и обоих дневальных. Указанные люди не назначаются на первое число. При пустом списке назначения предыдущего месяца неизвестны и граница месяца не проверяется.
- Каждый день назначаются по два уборщика кубаря своего взвода и два уборщика санузлов из любого взвода — шесть разных людей.
- Уборка запрещена в день наряда и на следующий день после наряда. Это также относится к первому числу, если заполнен `previous_month_last_day`.
- Один человек не может одновременно убирать кубарь и санузлы.

По четвергам ездящих в Сириус стараемся не назначать на уборки. Это предпочтение с высшим приоритетом, а не запрет: минимизация таких назначений важнее всех остальных штрафов вместе. В частности, при текущих 14 людях и 6 ездящих в Сириус строгий запрет сделал бы расписание невозможным. После наряда среды остаётся максимум 5 не ездящих уборщиков, а нужны 6.

В `cleaning.enabled` можно указать `false` для отдельного расчёта только нарядов; по умолчанию все три графика уборок включены.

Желательные правила оптимизируются совместно: выравнивается общая нагрузка (`completed_duties` плюс назначения за месяц), а близко стоящие наряды штрафуются. Параметр `preferred_gap_days` задаёт целевое расстояние между датами нарядов. Чем меньше расстояние относительно целевого, тем выше квадратичный штраф; расстояния не меньше целевого не штрафуются. `spacing_weight` и `balance_weight` задают компромисс между интервалами и балансом; значение `0` отключает соответствующий критерий. История содержит общее число нарядов, поэтому интервалы до предыдущих нарядов вне расчётного месяца, кроме указанной границы, не оцениваются.

Excel при включённых уборках содержит шесть листов:

- **По людям** — ФИО, дни месяца, отметки `Деж` и `Дн`, число дежурств и дневальных, общее число нарядов за месяц, история и итог с историей.
- **По дням** — дата, день недели, дежурный, два дневальных и все шесть уборщиков.
- **Кубарь 1 взвод**, **Кубарь 2 взвод**, **Санузлы** — отдельные графики с отметкой `У` и количеством уборок каждого человека. Все уборки оформляются одинаково.
- **Итоги** — наряды, уборки по каждому графику, суммарная нагрузка за месяц, общий штраф и статус оптимальности.

Для уборок отдельно настраиваются `cleaning_preferred_gap_days`, `cleaning_spacing_weight` и `cleaning_balance_weight` в разделе `preferences`. Предпочтение интервалов действует между любыми уборками одного человека, включая кубарь и санузлы. Кубари балансируются внутри каждого взвода, санузлы — между всеми людьми; учитываются уборки расчётного месяца, без истории уборок.

Каждое назначение считается одним нарядом независимо от роли. Выходные также включены. Счётчики в `people.yaml` автоматически не изменяются: рассчитанный план ещё не означает, что наряды отхожены.

Путь к Excel выводится после успешного расчёта. При шаблоне выше файл за декабрь 2026 года находится в `output/duties-2026-12.xlsx`. Новый месяц получает другое имя; повторный успешный расчёт того же месяца перезаписывает файл. При ошибке уже существующий Excel остаётся на месте, поэтому ориентируйтесь на сообщение текущего запуска.

Экспорт сначала записывает временный файл и заменяет прежний Excel после успешного сохранения. В таблицах нет специальных цветов, столбцов или подписей для уборок перед Сириусом; предпочтение при расчёте продолжает действовать.

Дополнительно `duty_role_weight` задаёт штраф за назначение допущенного к дежурству человека дневальным. Чем выше вес, тем сильнее предпочтение назначать таких людей именно дежурными. Значение `0` отключает этот критерий. Общее количество дежурств всегда равно числу дней месяца, поэтому максимизировать его сумму бессмысленно; критерий уменьшает число дневальных назначений среди допущенных к дежурству. Это предпочтение с весом, а не обязательный запрет: оно может уступать балансу и интервалам. Оптимальность относится к выбранной сумме всех штрафов.

### Настройки поиска

В разделе `solver` доступны:

| Параметр | Назначение |
| --- | --- |
| `name` | Имя установленного решателя: например, `chuffed`, `cp-sat` или `gecode`. |
| `time_limit_seconds` | Лимит в секундах; `null` — без ограничения времени. |
| `free_search` | Разрешить решателю выбирать свою стратегию поиска. Для Chuffed можно использовать `true`. |
| `random_seed` | Начальное значение генератора случайных чисел. Другие значения позволяют пробовать другие траектории поиска; улучшение не гарантируется. `null` — значение по умолчанию. |
| `processes` | Число процессов для поддерживающих параллельный поиск решателей. Для Chuffed оставьте `null`. |
| `optimisation_level` | Уровень оптимизации компиляции MiniZinc, от 0 до 5. Обычно достаточно 1; это не уровень качества расписания. |
| `require_optimal` | При `true` Excel создаётся только при доказанной оптимальности. При `false` можно выгрузить лучшее найденное допустимое решение. |

Параметры интеграции соответствуют [MiniZinc Python API](https://python.minizinc.dev/en/latest/api.html). Поддержка свободного поиска, начального значения генератора и процессов проверяется по конфигурации выбранного решателя; неподдерживаемый параметр вызывает понятную ошибку.

Для поиска до доказательства оптимальности укажите:

```yaml
solver:
    name: cp-sat
    time_limit_seconds: null
    free_search: false
    random_seed: null
    processes: 4
    optimisation_level: 1
    require_optimal: true
```

Поиск без лимита может занимать длительное время. При ограниченном времени решатель улучшает решение в пределах лимита; большее время не гарантирует улучшения или доказательства оптимальности. Итоговый штраф выводится в терминал и Excel: меньшее значение лучше при одинаковых исходных данных и весах.

Для поиска на нескольких ядрах CPU можно выбрать установленный OR-Tools CP-SAT:

```yaml
solver:
    name: cp-sat
    time_limit_seconds: 300
    free_search: false
    random_seed: null
    processes: 4
    optimisation_level: 1
    require_optimal: false
```

Доступность имени `cp-sat` проверяется командой `minizinc --solvers`. Число процессов подбирается под процессор и нагрузку. Chuffed и данный backend CP-SAT не используют GPU для поиска.

При достижении лимита времени и `require_optimal: false` сохраняется лучшее найденное допустимое расписание с пометкой, что оптимальность не доказана. Если решения нет или включён `require_optimal: true`, а оптимальность не доказана, новый Excel не создаётся; программа различает доказанную невозможность и отсутствие решения за отведённое время. Перед экспортом обязательные правила независимо проверяются в Python. Новый запуск начинает поиск заново и автоматически не продолжает предыдущий расчёт.

Проверки:

```bash
uv run python -m unittest discover -s tests -v
```

Проверка реального расчёта пропускается, если MiniZinc отсутствует; проверка Excel требует установленного `openpyxl`.
